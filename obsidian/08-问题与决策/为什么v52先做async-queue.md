# 为什么v52先做async-queue

## 结论

`v52` 最应该优先做 async queue / inbox，而不是先做审批流或长任务后台，因为调度收发是后续能力的基础。

## 背景

`v51` 已经补齐 session / message / transition。  
下一步最自然的是解决“这些消息如何挂起、接收、认领和完成”。

## 为什么不是先做审批

- 审批需要先有任务挂起点
- 没有 queue / inbox，审批很容易变成假的静态字段

## 为什么不是先做长任务生命周期

- 长任务状态依赖任务调度基础
- 没有 claim / pending / blocked，很难定义生命周期细节

## 当前判断

先 `v52`，后续再进入审批和长任务，更符合总纲。
