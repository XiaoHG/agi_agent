# RAG 本地检索阶段复盘

## RAG 和普通文件读取工具有什么区别？

- 普通文件读取工具只负责按路径读取指定文件，重点是“拿到这个文件的原文内容”。
- RAG 面向的是问题检索：系统会先加载一批本地文档，再切分成 chunk，然后根据用户问题检索相关上下文，最后把命中的上下文和来源返回给用户。
- 当前项目里的 `read_file` 是确定路径读取，`search_docs` 是基于问题搜索多个文档来源。

## 当前关键词检索为什么还不是完整 RAG？

- 当前实现只做了关键词匹配和简单计分，无法理解同义词、上下文语义和复杂表达。
- 当前还没有 embedding，没有向量索引，没有 rerank，也没有让 LLM 基于检索上下文生成自然语言答案。
- 所以它是 RAG 的最小工程闭环，但不是完整生产级 RAG。

## 为什么检索结果必须带来源？

- 来源可以让用户确认答案依据来自哪个文件和哪些行号。
- 来源可以帮助开发者判断检索是否命中了正确上下文。
- 来源也是后续做 RAG eval 的基础：没有来源，就很难判断答案是基于证据还是编造。

## 当前实现如果换成 embedding 检索，哪些模块可以保留？

- `rag/documents.py` 可以保留，因为文档加载仍然需要。
- `rag/chunking.py` 可以保留，因为向量检索也需要先切分文档。
- `rag/qa.py` 的整体编排可以保留，但内部检索步骤需要替换。
- `agent/tools.py` 和 `agent/router.py` 的接入方式可以保留，因为 Agent 不需要关心底层是关键词检索还是 embedding 检索。
- `rag/retrieval.py` 需要重点替换或扩展：从关键词计分升级为 embedding 检索、向量索引和 rerank。

## 下一步应该先做 MCP，还是先增强 RAG？

建议下一步先做 MCP 最小骨架。

原因：

- 当前 RAG 已经有最小闭环，可以支持学习 RAG 的主链路。
- 继续增强 RAG 会很快进入 embedding、向量库、rerank 和 LLM 答案生成，复杂度会明显上升。
- 课程路线的当前阶段是 “RAG 与 MCP”，所以应该先补齐 MCP 的最小闭环，再回头增强 RAG。
- MCP 建好后，后续可以把 RAG 或其他能力统一暴露成工具，更符合 Agent 工程化方向。

因此下一阶段建议目标是：

```text
MCP Server -> MCP Client -> Agent tool adapter -> CLI demo -> tests
```
