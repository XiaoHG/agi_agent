# 写作流程

更新日期：2026-08-18

## 1. 文件职责

这份文件是书稿撰写阶段的直接执行流程，用来回答两个问题：

1. 每一章应该按什么步骤写。
2. 写作过程中哪些边界是强制约束，不能靠作者临时判断。

后续继续写任何章节时，都应把本文件作为第一参考，而不是只依赖章节内的临时备注。

## 2. 标准流程

1. 版本与证据确认阶段
2. 章节范围与版本边界确认阶段
3. 章节提纲阶段
4. 正文初稿阶段
5. 技术审校阶段
6. 结构与承接审校阶段
7. 语言润色阶段
8. 章节锚点冻结阶段
9. 发布准备阶段

## 3. 强制写作约束

### 3.1 低版本章节不得串入高版本内容

如果当前章节介绍的是低版本内容，那么正文中不得提前展开后续高版本迭代出的能力、结构或实现细节。

允许：

- 用一句话说明“后续还会继续演进”
- 在章末做简短承接

不允许：

- 把后期结构体、协议、运行时能力直接写成当前版本内容
- 用当前仓库最新代码形态替代低版本历史状态

### 3.2 每章必须有清晰版本边界

每个章节都必须清楚说明自己对应：

- 一个版本
- 或一段连续版本区间

不允许把不连续的版本强行拼成同一章的主证据主线。

例如：

- 合理：`v05-v07`
- 不合理：`v05` 和 `v42` 直接作为同一章的同级主证据

### 3.3 章节必须承上启下

每章都必须回答三件事：

1. 它承接上一章解决了什么问题。
2. 它本章重点解决什么问题。
3. 它为什么自然引向下一章。

如果一章只能独立成立，却无法解释它在全书里的位置，说明结构仍不合格。

### 3.4 章节安排优先服从代码迭代主线

全书目录不是简单照抄版本顺序，但每章的核心证据必须尊重代码真实迭代主线。

规则如下：

1. 一个章节可以只对应一个版本。
2. 一个章节也可以合理覆盖多个版本。
3. 如果覆盖多个版本，这些版本必须连续。
4. 章节中的能力展开顺序，应尽量按对应版本的实际递进组织。

### 3.5 正文只讲“当前章应讲清楚的东西”

如果某个能力要到后续章节才正式展开，那么当前章只需要：

- 建立边界
- 说明当前限制
- 给出到下一章的过渡

不要在当前章提前把后续章节内容写透。

### 3.6 正文出现版本号时，必须给出查阅索引

如果正文或固定小节中出现了明确版本号，例如 `v03`、`v07`，就必须让读者可以立即追溯到对应材料。

允许的索引方式：

- `publish/version-index.md`
- `versions/` 目录中的对应版本文档
- 已经稳定创建的章节锚点 tag

如果当前章节做不到给出上述任一确定索引，就不要在正文中直接写出具体版本号。

## 4. 每章写作前必须先确认的五件事

1. 本章主锚点版本或版本区间是什么。
2. 本章是否只使用了连续版本作为主证据。
3. 本章正文是否混入了后续高版本才出现的实现。
4. 本章与上一章、下一章的承接关系是否已经写清楚。
5. 本章引用的代码入口是否与本章版本边界一致。
6. 如果正文中出现版本号，读者是否能通过版本索引、版本文档或标签立即查到对应材料。

如果其中任一项无法回答，不应直接进入正文扩写。

## 5. 每次迭代的最小产出

- 一份更新后的章节大纲
- 一条明确的版本边界说明
- 一段可引用的项目事实
- 一版章节草稿
- 一份修订记录
- 一条下一步写作任务

## 6. 审校重点

- 技术事实是否准确
- 术语是否统一
- 章节顺序是否合理
- 版本边界是否清晰
- 是否把高版本能力提前写进低版本章节
- 是否有跳步和缺证据的结论
- 是否把“项目演进”写成“静态总结”
- 是否真正写出了承上启下关系

## 7. 用于后续撰写的快速参考

后续开始写某一章时，先用下面这份检查表：

1. 这章讲的是哪个版本或哪段连续版本？
2. 这章是否错误引用了更高版本的结构或代码？
3. 这章的重点是否只围绕当前版本阶段应该解决的问题？
4. 这章开头是否承接上一章，结尾是否自然引出下一章？
5. 这章的代码入口、版本锚点和验证命令是否与版本边界一致？
