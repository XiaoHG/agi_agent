# 第 6 章 工具边界：从本地工具到 MCP 协议

状态与工作流解决了“系统如何管理一段过程”的问题，但当系统继续变大时，新的压力很快会出现：工具越来越多，调用方式越来越杂，权限和安全边界也越来越容易被忽略。到了这个阶段，Agent 已经不再只是“能做几次动作”，而是开始面对“这些动作应该如何被标准化地接入系统”的问题。工具如果仍然只以零散函数的形式存在，系统会很快陷入两个困境：一是调用路径不清楚，二是治理边界不清楚。

这正是工具边界成为独立章节的原因。一个专业的 Agent 系统，不能只把“能调用工具”当成目标，还必须把“工具如何被描述、如何被调用、如何被限制、如何被追踪”一起纳入设计。换句话说，工具不是附属小功能，而是 Agent 执行链路的一部分。只要工具开始参与主链路，就必须有自己的协议、自己的适配层和自己的验证方式。

本章对应的 MCP 早期阶段，处理的就是这条边界的最小版本。它没有直接上完整的外部 MCP SDK，也没有一开始就引入网络传输，而是先在本地进程内把工具协议的骨架搭起来。这样的做法看似朴素，但对学习项目非常重要，因为它能把“协议边界”从概念变成可观察的结构。读者可以清楚看到：工具 schema 如何定义，client 如何发起请求，server 如何处理调用，adapter 如何把两端接起来，Agent 又是如何把这些调用纳入统一执行面。

如果把这个过程先压缩成一条链路，那么本章想建立的最小理解可以画成这样：

```mermaid
flowchart LR
    A1[Agent 主链路] --> A2[MCP adapter]
    A2 --> A3[LocalMCPClient]
    A3 --> A4[LocalMCPServer]
    A4 --> A5[工具返回结果]
    A5 --> A6[统一输出]
```

这条链路的关键不在于“多了一层”，而在于“每一层都有明确职责”。`LocalMCPServer` 负责暴露工具，`LocalMCPClient` 负责调用边界，`mcp/adapter.py` 负责把协议层接进 Agent 可用接口，`agent/tools.py` 负责把 MCP 变成可路由工具，`agent/router.py` 再决定哪些请求应该走这条路径。如此一来，工具不再是代码里随手拼接的辅助函数，而是具备了正式边界的能力单元。

本项目当前的 MCP 学习层，核心文件集中在 `mcp/schema.py`、`mcp/servers/local_server.py`、`mcp/clients/local_client.py`、`mcp/adapter.py` 和 `mcp/policy.py`。其中，`schema.py` 定义了请求、响应、工具规格和执行记录；`local_server.py` 提供本地进程内的工具服务；`local_client.py` 则把 server 侧能力包装成 client 侧调用；`adapter.py` 负责把这些对象整理成 Agent 可以直接使用的接口；`policy.py` 再进一步把权限和请求校验从执行逻辑里拆出来。这样的拆分并不复杂，但它把“能运行”与“可治理”分开了。

这一点非常关键。很多原型系统在工具调用上容易犯的错误，是把“调用成功”当成唯一目标，却忽略了工具系统真正需要的是可控性。一个工具是否允许写文件，是否只读，是否越过工作区根目录，是否能被稳定复现，这些问题都不是调用一次就结束的。只要工具会影响项目状态，系统就必须能回答：这个工具是什么、它能做什么、它被谁调用、调用过程是否合规、失败之后应该如何回退。MCP 的价值就在于，它把这些原本容易混在一起的问题拆成了独立层次。

在这个项目里，MCP 不是拿来“炫技”的，它首先是一个训练边界感的装置。`mcp/servers/local_server.py` 里暴露了 `workspace_summary`、`read_project_file` 和 `write_project_file` 这类典型能力，既能让读者理解协议结构，也能看见权限边界如何生效。`tests/test_mcp.py` 进一步把这些行为变成回归测试，说明 MCP 不是单次演示，而是已经进入了项目的持续验证体系。对 Agent 工程来说，这比“有没有接上真实 SDK”更重要，因为只有边界足够清楚，后续接真实协议时才不会把系统搞乱。

从主执行面的角度看，MCP 进入系统后，路由逻辑也开始变得更有层次。`agent/router.py` 不再只是决定“直接回答还是调用本地工具”，而是还要识别“是否要列出 MCP 工具”“是否要通过 MCP 读取工作区文件”“是否要调用 MCP 工作区摘要”。`agent/core.py` 则把这些判断统一收束到 `_call_tool()`，确保工具层没有绕开主执行器直接返回。也就是说，MCP 并没有把 Agent 的执行主线切碎，反而把工具调用这件事重新放回了可控主链路中。

这章最值得强调的工程取舍，是本项目故意先实现“本地模拟的 MCP 骨架”，再去谈更完整的协议集成。原因很简单：学习阶段最重要的不是把生态接得最多，而是把边界看得最清楚。真实协议接入当然重要，但在那之前，先理解 client/server/adapter 的责任划分、权限校验的入口、错误返回的形态，以及工具输出如何回到 Agent 主链路，这些基础问题更关键。只要这些基础问题还不清楚，后续无论接多大的协议，都很容易退化成一层新的黑箱。

从读者学习路径来看，本章也承担着一个承上启下的作用。前一章讲的是状态与工作流，强调过程可以被组织起来；这一章讲的是工具边界，强调能力可以被标准化接入。下一章将进一步进入 Skills、Subagent 与角色协作，因为一旦工具边界被理顺，系统就会自然开始思考：哪些能力适合做成可复用技能，哪些任务适合委派给子代理，哪些操作又需要更明确的角色分工。换句话说，MCP 不是终点，它只是系统从“会执行”走向“会治理执行”的一个重要起点。

## 本章代码入口

- `mcp/schema.py`
  重点看请求、响应、工具规格和执行记录，理解协议层的基本形状。
- `mcp/servers/local_server.py`
  重点看本地 server 如何暴露工具、处理路径安全和返回错误。
- `mcp/clients/local_client.py`
  重点看 client 如何包住 server 调用边界。
- `mcp/adapter.py`
  重点看 adapter 如何把协议层转成 Agent 可调用接口。
- `mcp/policy.py`
  重点看权限策略和请求校验如何从执行逻辑中拆分出来。
- `agent/tools.py`
  重点看 MCP 工具如何进入统一工具目录。
- `agent/router.py`
  重点看路由如何识别 MCP 请求。
- `agent/core.py`
  重点看 `_call_tool()` 如何把 MCP 工具纳入主执行器。
- `cli/mcp_demo.py`
  重点看独立 demo 如何验证本地 MCP 骨架。
- `tests/test_mcp.py`
  重点看工具、协议和路由是否都被回归测试覆盖。

## 本章阅读与验证指引

读完本章后，建议按下面的问题自检：

1. 为什么工具一多，系统就不能继续把它们当作零散 helper？
2. 为什么协议层、适配层、权限层和执行层必须分开？
3. 为什么“能调用成功”不等于“已经具备可治理的工具边界”？
4. 为什么本地模拟的 MCP 骨架，比一开始直接接完整外部 SDK 更适合学习 Agent 工程？

再用下面的命令验证你的理解：

```bash
python -m cli.mcp_demo --list-tools
python -m cli.mcp_demo --tool workspace_summary
python -m cli.main --input "List MCP tools." --trace
python -m cli.main --input "Use MCP workspace summary." --trace
python -m cli.main --input "Use MCP to write notes.txt with content hello." --trace
pytest tests/test_mcp.py
```

如果你能说明以下三件事，说明本章已经真正读懂了：

1. 工具边界为什么要协议化。
2. 为什么 MCP 的关键不只是“工具调用”，而是“工具治理”。
3. 为什么本章完成后，系统会自然走向 Skills、Subagent 和角色协作。
