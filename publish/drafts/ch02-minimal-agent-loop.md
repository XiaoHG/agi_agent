# 第 2 章 最小 Agent 闭环

## 本章目的

这章要回答一个最基础、但也最重要的问题：一个 Agent 为什么不能只是“会回答问题”，而必须先有路由、工具和回答的分层。

如果没有这个最小闭环，后面的状态、工作流、RAG、MCP、Skills、LangGraph 都没有落点。

## 2.1 为什么先做闭环，而不是先做框架

很多人第一次做 Agent，会本能地想直接上复杂框架，或者一下子把所有能力都塞进一个大函数里。

但一个可维护的 Agent 项目，第一件事不是“功能多”，而是“链路清楚”。

最小闭环要解决的不是复杂智能，而是把下面这条路径先跑通：

```text
用户输入 -> 路由判断 -> 工具调用或直接回答 -> 最终输出
```

这个闭环一旦成立，后续所有扩展都能围绕它演进。没有闭环，后面的每个能力都会变成孤立 demo。

## 2.2 v01 先解决了什么

`v01` 的目标非常明确：先打通最小可运行 Agent 闭环。

这意味着项目先不追求复杂推理，也不追求多工具协作，而是先把最关键的执行边界建立起来：

- 输入从 CLI 进入系统。
- 路由把自然语言变成可执行决策。
- Agent 根据决策选择调用工具或直接回答。
- 最终结果写回 `AgentRun`。

这个阶段的价值在于，它让 Agent 从“一个会说话的程序”，变成“一个会决策的程序”。

## 2.3 最小闭环长什么样

可以把这个阶段理解成下面这条最小管线：

```text
CLI 输入
  -> route_intent()
  -> WorkspaceAgent.run()
  -> use_tool / direct_answer
  -> AgentRun.answer
```

这条管线很短，但它把 Agent 的核心职责拆开了：

- 路由负责判断。
- Agent 负责调度。
- 工具负责执行。
- answer 负责输出。

## 2.4 路由为什么是第一层能力

在这个项目里，`route_intent()` 是最先需要理解的函数之一。

它做的事情不是“理解世界”，而是把用户输入映射成系统能执行的动作。

例如：

- `use_tool`
- `direct_answer`

这一步很朴素，但非常关键。因为 Agent 不是把所有输入都丢给模型自由发挥，而是先做一次工程判断：当前请求应该走哪条路。

这就是 Agent 和普通聊天应用最早拉开的差异。

## 2.5 为什么 `WorkspaceAgent` 要分层

`WorkspaceAgent.run()` 并不是简单地把输入丢给一个大函数。

它把整个执行过程拆成几层：

1. 接收输入。
2. 生成路由。
3. 记录步骤。
4. 选择执行路径。
5. 调用工具或直接回答。
6. 记录结果和错误。
7. 返回结构化 `AgentRun`。

这样设计的好处不是“看起来更工程化”，而是后面每一步都能单独观察、单独测试、单独替换。

如果把所有逻辑塞成一段流程，后续只会得到一个越来越难维护的脚本。

## 2.6 典型 CLI 例子

v01 阶段的典型验证命令是：

```bash
python -m unittest tests.test_agent -v
python -m cli.main --input "Explain the difference between an agent and a chatbot." --trace
```

这类命令的意义不是“跑个演示”，而是确认：

- 路由能否稳定返回正确动作。
- 主链路能否从输入走到输出。
- trace 能否帮助我们看清执行过程。

## 2.7 为什么测试从一开始就要跟上

`tests/test_agent.py` 之所以重要，是因为它验证的不是某个细节，而是最小闭环是否稳定。

这个阶段的测试价值在于：

- 证明路由没有失效。
- 证明工具调用链没有断。
- 证明最终回答仍然可用。

也就是说，测试不是“附带的检查项”，而是 Agent 工程的基本护栏。

如果没有这个护栏，后面的每次扩展都可能把最基础的闭环改坏。

## 2.8 v02 为什么紧接着引入状态与工作流

`v02` 很自然地接在 `v01` 后面，因为最小闭环已经能跑了，但还不能处理多步任务。

于是项目开始引入：

- `AgentState`
- `WorkflowPlan`
- 顺序执行
- 工作流结果汇总

这说明一个重要原则：先把单步闭环做好，再在同一条链路上增加状态和步骤。

如果没有 `v01` 的闭环，`v02` 的工作流就没有稳定的执行底座。

## 2.9 本章结论

最小 Agent 闭环的真正意义，不是“做了一个最简版本”，而是建立了 Agent 工程的基本骨架。

这套骨架至少要包含四层：

- 路由层：决定走哪条路。
- 工具层：执行具体动作。
- 输出层：生成最终回答。
- 测试层：保证闭环不被改坏。

后续任何能力，不管是状态、RAG、MCP、Skills 还是 LangGraph，最终都要回到这四层里。
