# 第 1 章 为什么要把这个项目写成一本书

## 本章目的

把项目学习过程整理成一本书，不是为了把零散笔记重新排版，而是为了把一个持续演进的 Agent 工程项目，沉淀成可复用、可教学、可回顾的专业知识体系。

## 1.1 这本书从哪里来

这本书不是从“写书”开始的，而是从一个长期演进的本地 Agent 学习项目开始的。

这个项目最初的目标很简单：先跑通一个最小 CLI Agent，让系统具备输入、路由、工具调用和回答生成的完整闭环。随后，项目逐步扩展到状态与工作流、本地 RAG、本地 MCP、Skills 与 Subagent、真实 LLM 接入、tool calling、tool loop、LangGraph 编排，以及可观测性、评估、恢复和权限策略。

换句话说，这本书并不是在项目之外“总结项目”，而是把项目本身的演进过程，整理成一条可阅读、可复盘、可继续生长的主线。

## 1.2 为什么不能只把文档堆在一起

如果只是把 `docs/` 和 `versions/` 中的内容按时间顺序排列，它们仍然只是笔记集合，不是书。

书需要三层结构：

- 叙事结构：读者知道为什么从这里开始，为什么到这里结束。
- 知识结构：概念有层次，先讲基础，再讲扩展。
- 工程结构：每一章都能落回项目文件、版本、测试和验证命令。

这个项目已经具备把书写成“工程知识书”的条件，因为每个阶段都有版本文档、练习文档、当前学习状态、代码实现和验证路径。书稿只需要把这些材料组织成稳定章节，而不是重新发明内容。

## 1.3 这本书要解决什么问题

这本书主要解决三个问题。

第一，帮助读者理解 Agent 不是聊天界面，而是一个有路由、工具、状态、记忆、评估和恢复机制的执行系统。

第二，帮助读者看到专业 Agent 不是一次性做大模型接入，而是沿着清晰阶段不断补齐工程边界：最小闭环、工作流、RAG、MCP、Skills、LangGraph、trace、eval、checkpoint。

第三，帮助读者建立一种可迁移的方法：遇到新的 Agent 能力，不是先堆代码，而是先定义数据结构、执行边界、验证方式和下一阶段接口。

## 1.4 为什么这个项目适合写成书

这个项目适合写成书，因为它天然具有阶段性。

每个版本都在解决一个明确问题：

- v01 先把最小 Agent 闭环跑通。
- v02 让 Agent 能处理状态和工作流。
- v03 和 v04 把 RAG 与 MCP 拉进系统边界。
- v05 到 v07 让 Skills、Subagent 和学习工作台成型。
- v08 到 v14 让真实 LLM、RAG、LangGraph 和主链路接回逐步落地。
- v15 到 v35 则进一步推进 tool calling、tool loop、runtime events、checkpoint、registry、permission 和 graph 化执行。

这种演进方式非常适合写书，因为它不是“功能列表”，而是“能力生成史”。

## 1.5 这本书应该怎么写

这本书不应该按目录软件化地堆概念，而应该按项目演进来写。

每一章都要回答四个问题：

1. 这一阶段在解决什么问题？
2. 为什么前一阶段不够？
3. 代码里如何体现这个能力？
4. 下一阶段还缺什么？

这样写出来的书，既能给初学者建立清晰路径，也能给已经做过项目的人提供复盘框架。

## 1.6 本章结论

这本书的价值，不在于把项目材料重新整理一遍，而在于把一个 Agent 学习项目变成一条可持续学习和写作的知识链路。

项目代码负责验证能力，`docs/` 和 `versions/` 负责记录演进，`publish/` 负责把演进写成可出版的书。

## 1.7 下一章

下一章会进入最小 Agent 闭环，解释一个 Agent 为什么必须先有路由、工具和回答的分层，而不能把所有逻辑塞进一个函数。

## 1.8 版本案例

| 版本 | 说明 | 对本书的意义 |
| --- | --- | --- |
| v01 | Minimal CLI Agent | 证明最小闭环能跑通 |
| v02 | 状态与工作流 | 证明闭环之后可以继续扩展多步执行 |
| v03 | 本地 RAG 最小闭环 | 证明知识检索可以进入 Agent 主链路 |
| v29 | Professional RAG v1 | 证明项目已经进入专业化能力阶段 |

## 1.9 引用方式

这一章的结论主要来自：

- 学习总纲
- 当前学习状态
- 版本演进文档
- 主执行器和路由代码

后续写章时，所有结论都应尽量对应到版本、代码或测试，不写没有证据的判断。
